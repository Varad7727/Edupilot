# Authentication

## Overview

Authentication is implemented in `backend/controller/auth.controller.js` and
`backend/middleware/auth.middleware.js`, with routes in
`backend/routes/auth.routes.js`. Student and teacher accounts use bcrypt
password hashes and JWTs stored in an HTTP-only cookie named `token`.

## Registration and login

Student and teacher registration endpoints accept `firstName`, `lastName`,
`email`, and `password`. Controllers trim names, normalize email to lowercase,
hash the password with `bcrypt.hash(password, 10)`, save the account, sign a
JWT, and set the cookie. The JWT payload contains the user ID and role. A
successful registration returns HTTP `201`.

Login normalizes the email, fetches the corresponding model, and verifies the
password with `bcrypt.compare`. On success, the controller signs and sets a
JWT and returns HTTP `200`. Invalid credentials and missing input return
HTTP `400`.

Relevant files:

- `backend/routes/auth.routes.js`
- `backend/controller/auth.controller.js`
- `backend/model/student.model.js`
- `backend/model/teacher.model.js`

## JWT and cookie behavior

- JWT algorithm: `HS256`
- JWT lifetime: one day (`expiresIn: "1d"`)
- Signing/verifying secret: `JWT_SECRET`
- Cookie name: `token`
- Cookie flags: `httpOnly: true`, `sameSite: "strict"`
- Cookie `secure`: true only when `NODE_ENV === "production"`
- Cookie max age: one day

The token is created on successful registration and login. There is no refresh
token endpoint or server-side session store. No server-side token revocation
list is implemented.

The logout route clears the cookie using `httpOnly`, the same environment
dependent `secure` flag, `sameSite: "strict"`, and path `/`. Logout does not
invalidate a previously copied JWT; the token remains cryptographically valid
until expiry.

## Authentication middleware

`authStudentMiddleware` and `authTeacherMiddleware`:

1. Read `req.cookies.token`.
2. Return `401` if the cookie is absent.
3. Verify the JWT using `JWT_SECRET`.
4. Return `403` if the token role does not match the route.
5. Load the referenced Student or Teacher and attach it to `req.student` or
   `req.teacher`.

The current middleware catches verification and model lookup errors in the
same `try/catch` and reports them as `401 Invalid Token!!`. It does not
explicitly return an error when a valid token's ID no longer maps to a user;
it assigns `null` and calls `next()`. Downstream behavior then depends on the
route/controller.

**Student role mismatch in the current implementation:** registration and
login sign student JWTs with role `"student"`, but
`authStudentMiddleware` compares the role to `"Student"` (capital `S`).
Consequently the token generated by the student auth endpoints does not pass
the student middleware and `POST /auth/student/logout` returns `403`. The
teacher role uses lowercase `"teacher"` consistently.

## Protected routes

| Role | Protected routes |
|---|---|
| Student | `POST /auth/student/logout` |
| Teacher | `POST /auth/teacher/logout`, `GET /teachers/me`, `PATCH /teachers/update`, and all `/teachers/chapters` routes |

Course and subject catalog endpoints are public.

The student logout route is nominally protected by the student middleware,
but the role mismatch above currently prevents tokens issued by student
registration/login from reaching its logout controller.

## Security and implementation notes

- Passwords are not returned from registration/login response objects.
- Teacher profile `PATCH` excludes the password from its success response.
- Current teacher profile `GET /teachers/me` returns the full Mongoose
  document without excluding `password`. The persisted value is hashed, but
  the hash is still sensitive and the response should not be treated as
  public.
- The Express app calls `cors()` without options. Cross-origin cookie behavior
  is not explicitly configured in this backend; deployments should verify
  browser origin and credential settings.
- `JWT_SECRET` has no code-defined fallback. Use a private, high-entropy value
  and do not commit it.
- The cookie is marked `secure` only when `NODE_ENV` equals `"production"`.
  HTTPS deployment behavior depends on setting that environment value.
